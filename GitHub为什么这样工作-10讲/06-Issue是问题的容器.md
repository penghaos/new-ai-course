# Issue 是问题的容器

> 一句话定义：Issue 是把模糊抱怨转成可讨论、可分工、可验收问题的容器。

## 一、很多人不是不会做，而是不知道自己到底要做什么

“首页不好看，优化一下。”

“登录有问题，修一下。”

“课程太简单，再深入一点。”

这些话看起来像任务，其实只是情绪。什么叫好看？哪个登录场景？深入到什么程度？谁做？什么时候算完成？

如果你不先回答，开发者就会替你猜。猜对了叫默契，猜错了叫返工。

我以前也很喜欢“先做起来再说”。看上去行动力强。做了两小时才发现，真正的问题还没想清楚；又做两小时，把错误方向打磨得更精致。哈，忙得很，进展为零。

行动之前最昂贵的错误，是问题定义错误。

Issue 就是用来装问题的。

## 二、Issue 不是报错单

Issue 常被翻译成“问题”，于是很多人只在发现 Bug 时才用。可 GitHub 官方对它的定位更广：想法、反馈、任务、缺陷，都可以用 Issue 计划、讨论和追踪。

更有用的理解是：

**凡是值得被项目记住、讨论、分配和关闭的工作，都可以进入 Issue。**

它可以是一项新功能、一次文档修订、一项研究任务、一个安全风险、一场需要决定的争论。

Issue 不是“出事了”。

Issue 是“有一件事需要形成共同理解”。

## 三、把抱怨洗成问题

一个可执行 Issue 至少回答四件事：

1. 当前发生了什么；
2. 为什么值得处理；
3. 期待变成什么状态；
4. 如何判断已经完成。

例如，别写：

```text
首页不好用。
```

改成：

```markdown
## 现状
新读者打开 README 后，只能看到课程介绍，找不到第一课入口。

## 影响
读者需要滚动并猜测学习顺序，容易直接离开。

## 期望结果
首屏出现“从这里开始”，链接到第 1 课。

## 完成标准
- [ ] README 首屏出现入口
- [ ] 链接在网页端可打开
- [ ] 不重写课程正文
```

你看，任务没有变长多少，歧义却少了大半。

好 Issue 不是写得多。

是让猜测变少。

## 四、完成标准为什么如此重要

“做一个搜索功能”和“用户能按标题搜索，空关键词显示全部，响应时间在现有数据量下可接受”，是同一个任务吗？

前一句只能启动工作，后一句才能结束工作。

很多项目不断拖延，不是大家不努力，而是没有可关闭的定义。每次看起来快做完了，又有人补一句“顺便支持标签呗”“最好还能导出”。任务边界不断移动，完成永远后退。

完成标准是终点线。

没有终点线，跑得再快也无法完赛。

这也是为什么 Issue 里最好写“不包含什么”。边界不是偷懒，而是保护当次交付。超出范围的好想法可以另开 Issue，别把所有愿望塞进一辆车。

## 五、Issue 与 PR 是问题和答案

Issue 说：我们观察到一个问题，希望达到某种状态。

PR 说：这里有一组具体变化，我认为它能解决那个问题，请审查。

两者关联后，项目历史就不再只有“做了什么”，还有“为什么做”。在 PR 描述中写 `Closes #42` 一类关联关键词，合并后可自动关闭对应 Issue。

这条连接很重要。

半年后你看到一段奇怪代码，可以从提交进入 PR，从 PR 回到 Issue，理解当时的限制和目标。代码是答案，Issue 保存题目。没有题目，答案看起来就可能莫名其妙。

一个健康的变化链是：

```text
观察 → Issue → Branch → Commit → PR → Review → Merge → Issue 关闭
```

这就是可追溯性。

## 六、标签、负责人和里程碑到底在解决什么

标签不是给 Issue 涂颜色。它帮助你从一堆工作中快速筛选类型、状态和风险。例如 `bug`、`documentation`、`priority:high`、`good first issue`。

Assignee 不是荣誉称号。它回答“谁正在推动这件事”，避免两个人重复劳动，也避免所有人都以为别人会做。

Milestone 不是漂亮的进度条。它把一组 Issue 与某个版本或时间目标连接起来。

工具背后分别是三种问题：这是什么，谁负责，何时一起完成。

如果标签多到没人记得含义，负责人只是名义挂靠，里程碑每次都延期，那么工具越丰富，幻觉越严重。

元数据不能替代真实进展。

## 七、大问题为什么要拆成子问题

“重做整个课程网站”不是一个适合直接开工的 Issue。它至少包含信息结构、视觉设计、内容迁移、搜索、移动端、部署和旧链接兼容。

大问题会产生两种错觉：第一，大家都知道它很重要；第二，没有人知道今天具体做什么。

拆分的标准不是越细越好，而是每个子问题都能独立推进、验证和关闭。GitHub 现在也支持 sub-issues 和依赖关系，用来表示层级与阻塞。

可别一上来就建几十层树。先问：哪个最小结果能让我们学到东西或解除阻塞？

拆任务的目的不是管理人。

是制造反馈。

## 八、Issue 和 Discussion 不要混用

有明确问题、需要行动并最终关闭，适合 Issue。开放式问答、经验交流、公告、还没形成行动的想法，往往更适合 Discussion。

“首页链接失效”是 Issue。

“大家怎样组织学习笔记更有效”可能是 Discussion。

当然，讨论最后可能形成一个具体任务，再转成 Issue。容器不同，是因为对话预期不同：一个要收敛到行动，一个可以展开观点。

先确定对话要不要结束。

再选择容器。

## 九、How：把一个抱怨改写成 Issue

打开你的 `my-ai-learning` 仓库，创建新 Issue。原始抱怨是：

```text
学习资料太乱。
```

不要直接动手。先补齐：

```markdown
## 现状
资源链接分散在 README 和学习日志中，存在重复与失效链接。

## 影响
复习时无法快速按主题找到资料。

## 期望结果
建立统一的 `resources/README.md`，按主题整理链接。

## 完成标准
- [ ] 至少包含 GitHub、AI 工具两个分类
- [ ] 每条资源有名称、链接和一句用途说明
- [ ] 删除重复链接
- [ ] 所有链接已人工打开检查

## 不包含
本次不下载和重新发布原始资料。
```

创建后，先别写文件。隔十分钟重新读一遍，问：另一个完全不了解背景的人，能否仅凭这份 Issue 开始工作并判断完成？

如果不能，继续洗概念。

## 十、开始工作前的唯一问题

别问：“我今天能做点什么？”

问：“什么变化出现后，这个问题才算被解决？”

前者制造忙碌，后者制造结果。

> 先把问题写到能关闭，再开始行动。
