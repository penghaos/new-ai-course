# Commit 是给变化办身份证

> 一句话定义：Commit 是一组有边界、有说明、可追溯的变化，而不是一次“保存”。

## 一、保存了，为什么还要提交

你在编辑器里按下 `Command + S` 或 `Ctrl + S`。文件保存了。

然后 GitHub Desktop 还在等你 Commit。命令行也告诉你有 changes not staged for commit。你难免会想：我不是已经保存了吗？

问得好。

我刚学 Git 时，最讨厌的就是这一步。保存一次，add 一次，commit 一次。感觉像去窗口办事，明明身份证已经递过去了，工作人员又让你复印一份，再填一张表。繁琐嘛。

后来我才明白：保存解决的是“文件有没有写进硬盘”，**提交解决的是“这次变化是否值得成为历史”**。

一个是物理动作。一个是认知决定。

## 二、不是所有变化都应该一起进入历史

假设你花了两个小时修改课程：

- 修正第一课的错别字；
- 新增第二课的练习；
- 删除一个不该公开的临时文件；
- 顺手改了首页配色；
- 测试了一个失败的目录结构；
- 下载了一个 300MB 的视频。

这些都发生在你的工作区里。可它们应该一起成为一个提交吗？

当然不应该。

错别字是一件事，练习是一件事，配色又是一件事。失败实验可能根本不该提交，视频也许不该放进 Git。若你把它们揉成一团，写一句“今天的修改”，未来谁能看懂？

所以 Git 在工作区和历史之间放了一个暂存区。暂存区说白了就是“下一张合照里，谁可以入镜”。

工作区里可以很乱。提交必须有边界。

## 三、Commit 是变化的身份证

一个提交通常包含几类关键信息：

- 哪些内容发生变化；
- 它基于哪个更早的提交；
- 谁创建了它；
- 什么时候创建；
- 提交者写下的说明；
- 一个由内容和历史计算出的标识。

因此，Commit 不只是快照。更准确地说，它是变化的身份证。

没有身份证的变化，只是一堆散落在工作区里的痕迹。有了提交，它才进入历史，能够被比较、引用、合并、撤销、推送和审查。

你可能会说：“我一个人做项目，写那么清楚给谁看？”

给三个月后的你看。

相信我，**你并不比同事更了解三个月后的自己**。我们总是高估记忆，低估上下文消失的速度。今天你觉得“这还用解释”，三个月后你只看到某段内容被删掉，却完全想不起为什么。

未来的你，也是协作者。

## 四、小提交不是洁癖，而是降低调查成本

有两种提交。

第一种叫“周末大礼包”：改了 27 个文件，增加功能、修复错误、升级依赖、重排格式，提交说明写 `update`。

第二种是三四个小提交：

```text
docs: 修正文档安装步骤
feat: 增加学习进度统计
test: 覆盖空数据场景
chore: 升级 Markdown 检查工具
```

哪一种更专业？

别急着答“第二种”。先问为什么。

因为小提交让四件事变便宜：理解、审查、定位、撤销。

如果系统突然出错，你可以逐个检查最近的变化。如果某项改动不合适，可以撤销那一块，而不是把一周工作整包扔掉。如果审查者只关心功能，不必同时吞下一堆格式变化。

小提交不是为了让历史看起来漂亮。

是**为了让错误便宜**。

## 五、可原子化：一个值得安装进脑子的概念

数据库里有一个概念叫“原子性”：一组操作要么完整成功，要么完整失败，不留下半截状态。

提交也应该尽量原子化。说白了，一个提交做完一件完整且可以单独解释的事。

修复登录问题时，代码和相应测试可以属于同一提交，因为缺一边都不完整。可“顺便重写首页文案”就不属于它。即使两个改动都很好，也不该绑在一起。

你去超市买苹果和洗衣机，当然可以一次结账。但若发票上只写“物品若干”，以后退货就麻烦了。**提交就是工作发票**。写清每一笔，麻烦才不会滚到未来。

## 六、提交说明不是作文，是索引

很多新手写提交说明时有两个极端。

要么写 `修改`、`update`、`final`，几乎没有信息。要么写一大段情绪和过程，却看不出到底改变了什么。

好的第一行只需准确概括动作：

```text
docs: 添加 GitHub 新手练习
fix: 修复首页失效链接
feat: 支持按日期筛选学习记录
```

为什么用动词？因为提交记录的是**变化**。名词只告诉你对象，动词才告诉你发生了什么。

若“为什么”不明显，再补正文：

```text
fix: 调整学习日志链接

文件移动到 notes 目录后，首页仍指向旧路径，导致链接失效。
```

标题负责扫描，正文负责解释。多简单且明了的道理啊！

## 七、Add 的真正意义是编辑历史

`git add` 经常被翻译成“添加文件”。这个翻译害了不少人，因为你会以为它只是把新文件加进去。

事实上，`git add` 做的是**把当前变化放入暂存区**。新建、修改、删除，都可以被暂存。

这意味着什么？

意味着你不是被动地把“今天做过的一切”塞进历史。你是在主动编辑历史：这一次提交应该讲一个什么故事？哪些变化属于这个故事？哪些留到下一次？

你看，Git 的设计又一次把判断权交给人。

工具不替你决定边界。

## 八、为什么提交之后 GitHub 可能仍然没变化

因为 Commit 默认发生在本地仓库。

Git 是分布式的。你的电脑有一份完整仓库，GitHub 上有另一份。你在本地提交，只更新了本地历史；直到 Push，这些提交才被发送到远端。

这不是缺陷。它让你离线也能工作，让你可以先在本地整理提交，再选择什么时候与别人共享。

**保存、提交、推送**，分别对应三个范围：

```text
保存：当前文件
提交：本地历史
推送：共享远端
```

范围越来越大，影响越来越广，所以决定也应该越来越慎重。

## 九、How：亲手拆出两个提交

在你的 `my-ai-learning` 仓库中新建分支：

```bash
git switch -c docs/practice-small-commits
```

然后做两类变化：

1. 在 `README.md` 增加“学习目标”；
2. 新建 `学习日志.md`，写下今天的收获。

先观察：

```bash
git status
git diff
```

只提交 README：

```bash
git add README.md
git diff --staged
git commit -m "docs: 补充仓库学习目标"
```

再提交学习日志：

```bash
git add 学习日志.md
git diff --staged
git commit -m "docs: 记录 Commit 学习心得"
```

最后查看：

```bash
git log --oneline -5
```

你会看到，同一次工作被整理成两笔清楚的历史。这就叫给变化办身份证。

## 十、提交前的三个问题

以后每次 Commit 前，问自己：

1. 这次提交只讲一件事吗？
2. 别人只看说明，能猜到变化方向吗？
3. 如果单独撤销它，项目会不会陷入半成品？

三个答案都满意，再提交。

别追求“没有脏文件”。追求“每一笔历史都说得清”。

> 提交越清楚，错误越便宜。
