# Review 与 Actions 是信任生产线

> 一句话定义：Review 与 Actions 把“我觉得没问题”转换为可重复检查的证据。

## 一、“相信我”是最昂贵的质量保证

“我已经测试过了。”

“这个改动很小，不会有问题。”

“只是改文档，不用审查。”

你听着熟悉吗？我不只听过，还说过。最尴尬的是，每当我信心最满时，错误往往藏得最好。不是因为人坏，也不是因为人笨，而是作者天然看不见某些东西。

你知道自己想表达什么，于是会自动补全缺失的字。你知道代码的预期路径，于是容易只测试那条路径。你刚花三小时完成它，大脑还会偷偷替自己的劳动辩护。

作者不是不可信。

作者只是视角不完整。

## 二、Review 不是审批，是视角交换

很多人把 Code Review 理解成上级检查下级。于是作者紧张，审查者摆架子，评论变成权力表演。

这完全搞反了。

更有用的定义是：Review 是让另一个视角检验变化是否符合目标、质量标准和长期维护需要。

作者拥有实现上下文，审查者拥有距离。作者知道为什么这样做，审查者更容易发现别人为什么看不懂。双方交换视角，项目才获得比任何单个人更完整的判断。

眼睛离书太近，字会糊。

退一步，才看得清。

## 三、先审问题，再审实现

差的审查一打开 PR 就逐行挑语法。好的审查先问：这是不是正确的问题？变化范围是否匹配目标？有没有更简单的路径？

若方向错了，代码写得再漂亮也是精致的浪费。

建议顺序是：

1. 阅读 Issue 和 PR 背景；
2. 看文件列表与总体差异；
3. 判断范围和设计；
4. 再逐文件检查正确性、安全性与可维护性；
5. 按作者给出的步骤实际验证；
6. 给出 Comment、Approve 或 Request changes。

从大到小。

先看森林，再看树皮。

## 四、好评论必须让下一步变清楚

“这里不优雅。”没用。

“建议优化。”也没用。

评论至少应说明：观察到什么，可能造成什么影响，为什么重要，建议如何验证或修改。

例如：

```text
当前实现把空列表和加载失败都显示为空白页，用户无法区分“没有数据”与“系统出错”。
建议分别显示空状态和错误提示，并覆盖这两个场景。
```

至于纯偏好，明确标记 `nit` 或“非阻塞建议”。不要把“我喜欢这样”伪装成“必须这样”。

审查的目标是提高结果质量，不是证明审查者聪明。

暴露的靶子应该是问题。

## 五、为什么机器检查必须自动化

假设团队规定：每次合并前都要运行测试、检查格式、确认链接、扫描依赖。

如果靠人记，会发生什么？忙的时候忘，急的时候跳过，新人不知道，老人在脑子里有不同版本。规则存在于文档，却不稳定地存在于行动。

GitHub Actions 把规则变成事件触发的工作流。有人 Push 或创建 PR，机器自动运行预定检查，再把结果放回 PR。

它的基本结构并不神秘：

```text
事件 Event → 工作流 Workflow → 作业 Job → 步骤 Step → 结果
```

门一开，灯自动亮。不是因为灯更聪明，而是触发关系被固定了。

自动化的意义不是少点几下。

是让规则不靠记忆。

## 六、绿灯为什么不等于正确

Actions 全绿，能合并了吗？

未必。

机器只会检查你教它检查的东西。没有测试的场景，它不知道；测试本身写错，它也会忠实通过；业务目标是否合理、用户体验是否变差、权限是否过大，往往仍需人判断。

机场安检通过，证明你符合已设定的安全检查，不证明你的旅行计划正确。体检指标正常，也不代表人生决策正确。

所以，人审与机审不是替代关系：

- 机器擅长快速、重复、一致；
- 人擅长语义、权衡、边界、责任。

让机器处理可形式化规则，让人把注意力留给不可形式化判断。

分工，才是自动化。

## 七、分支保护是在关键入口加门

如果仓库允许任何有写权限的人直接推送到 `main`，即使团队口头约定“要先开 PR”，忙起来也可能绕过。

保护分支或 Ruleset 可以把约定变成系统限制：要求 PR、要求审批、要求状态检查、限制强制推送和删除等。

规则的意义不是不信任同事。飞行员也要清单，医生也要核对，财务也要复核。专业系统假设人会疲劳、会误解、会犯错，因此把关键动作设计成不依赖完美人类。

制度不是对人的侮辱。

制度是对人性的诚实。

## 八、检查越多不一定越安全

有些团队把十几项缓慢检查全部设为必须，每个小改动都等半小时。结果如何？大家开始厌恶流程，想办法绕过，或者把许多变化攒成一个巨型 PR，以减少等待次数。

安全措施本身也有成本。好的检查应满足：与真实风险相关、失败信息可行动、运行时间可接受、维护责任明确。

无价值的红灯会训练人忽略红灯。这叫警报疲劳。医院监护器一直乱叫，最后没人认真听，真正危险的信号反而被埋没。

不是检查越多越专业。

是每个检查都值得信任。

## 九、How：给 PR 加一条最小自动证据

在练习仓库创建 `.github/workflows/hello.yml`：

```yaml
name: hello-actions

on:
  pull_request:
  workflow_dispatch:

jobs:
  say-hello:
    runs-on: ubuntu-latest
    steps:
      - name: 输出检查信息
        run: echo "这个 PR 已触发自动工作流"
```

在新分支提交并推送，创建 PR。打开 Actions 或 PR checks，观察：

1. 什么事件触发了它；
2. 哪个 Job 被运行；
3. Step 输出了什么；
4. 结果如何反馈到 PR。

这个工作流几乎不检查质量，但它让你看懂了自动化骨架。下一步再把 `echo` 换成真正的链接检查、测试或格式检查。

只使用可信 Action，固定合适版本，给予最小权限，绝不把秘密打印到日志。

## 十、合并前的证据清单

以后不要问：“大家觉得可以了吗？”

问：

- 目标是否清楚；
- 差异是否在范围内；
- 人工验证是否完成；
- 自动检查是否覆盖关键规则；
- 审查意见是否处理；
- 剩余风险是否被看见；
- 出问题能否回退。

信任不是一句话。

信任是证据的累计。

> 别要求别人相信你，给他可以检查的证据。
