# 本地与远端是两本可以对账的账簿

> 一句话定义：本地仓库和远端仓库各有一份历史，clone、fetch、pull、push 负责让它们交换与整合提交。

## 一、所有方向混乱，都来自参照物不清

Push 是上传，Pull 是下载。很多教程这么教。

初学时够用，遇到真实协作就不够了。因为 Git 交换的不是普通文件，而是提交和分支历史。更要命的是，“上”和“下”只是空间隐喻，真正重要的是从谁到谁。

我早期最常犯的错，就是把 GitHub 当唯一真身，把本地当临时副本。网站上的叫“项目”，电脑里的叫“下载下来的文件”。于是本地提交之后，我总觉得还没真正保存。

可 Git 是分布式版本控制系统。

你的本地仓库不是残缺副本。它有文件，也有完整历史，离线照样能提交、建分支、比较和合并。GitHub 上的远端仓库也有一套历史。二者更像两本账簿，需要定期对账。

不是主人和影子。

是两个仓库。

## 二、Clone 不是下载 ZIP

下载 ZIP，你得到的是某个时刻的文件。Clone，你得到的是文件、提交历史、分支信息和远端关联。

区别像什么？

下载 ZIP 像拿到一本书的复印件。Clone 像拿到整套版本档案，还附上出版社地址，以后能收新版，也能把自己的修订送回去。

```bash
git clone https://github.com/用户名/仓库名.git
```

执行后，Git 通常把来源地址记为一个叫 `origin` 的远端。

`origin` 并不等于 GitHub，也不是不可修改的系统关键词。它只是默认远端的惯用昵称。你完全可以连接多个远端，例如自己的 Fork 叫 `origin`，原项目叫 `upstream`。

名字可以骗你。地址不会。

所以遇到混乱先看：

```bash
git remote -v
```

## 三、Push 发送的是提交，不是尚未提交的文件

你修改文件，保存，然后执行 `git push`。Git 却说 Everything up-to-date。

你可能会怀疑它眼瞎了。明明文件变了呀。

Git 没瞎。变化还停留在工作区，尚未成为提交。Push 的工作是把本地仓库中远端没有的提交发送过去。它不负责替你决定哪些零散文件值得进入历史。

完整链条是：

```text
修改并保存 → add → commit → push
```

每一步扩大一个范围：工作区、暂存区、本地历史、共享远端。

影响越大，越需要明确决定。

## 四、Fetch 是看账，Pull 是对账

远端可能有同伴的新提交。本地还不知道。怎么办？

`git fetch` 会获取远端的新对象和分支状态，却不自动把它们整合进你当前正在工作的分支。它更像先拿到对方账本的最新副本，让你看看差异。

`git pull` 通常会先 fetch，再把对应远端分支的变化整合到当前分支。它不只是“下载”，还可能改变你眼前的工作历史。

所以可以这样记：

- Fetch：告诉我远端发生了什么；
- Pull：把远端变化整合到我这里；
- Push：把我的提交发送到远端。

先看，再合，再发。

## 五、为什么 Push 会被拒绝

你本地有提交 A，同伴已经把提交 B 推到同一个远端分支。此时远端历史比你多一步。Git 可能拒绝你的 Push，因为直接接受可能让对方变化从分支线上消失。

这时工具不是刁难你，而是在问：“远端账簿已经有新记录，你确认要无视吗？”

普通做法是先同步：

```bash
git pull
# 如有冲突，解决并检查
git push
```

最危险的反应是什么？搜索错误信息，复制第一条 `git push --force`。

强制推送的意思近似于：“别管远端发生过什么，以我这里为准。”在个人短期分支上，它有受控用途；在共享主线里，它可能覆盖别人工作。

工具给你刹车，你却拆掉刹车。怪谁呢？

## 六、分布式不是技术炫耀，而是权力设计

为什么 Git 要让每个人拥有完整历史，而不是所有操作都依赖中央服务器？

第一，你可以离线工作。第二，即使某个服务器不可用，仓库历史仍有多个完整副本。第三，每个人都可以先独立形成提交，再选择如何共享。第四，任何一份仓库都可以连接不同远端。

这不只提升可靠性，也改变协作权力。

开源贡献者不必先获得原项目写权限，便可以 Fork、Clone、提交，再通过 PR 提议合并。维护者控制主线，贡献者保有工作自由。双方用历史和提案连接。

分布式不是“服务器多一点”。

是先独立，再协商。

## 七、认证为什么独立于提交身份

这里还有一个常见混乱：提交里的名字邮箱，与向 GitHub 推送时的登录认证，不是同一件事。

`git config user.name` 和 `user.email` 决定提交记录显示的作者信息。认证则证明你有权访问某个远端。前者像文件署名，后者像门禁卡。

门禁卡通过，不代表署名一定正确；署名写对，也不代表你有推送权限。

GitHub 的命令行 Git 操作已经不使用账号密码认证。HTTPS 通常使用凭证管理器、浏览器授权或个人访问令牌；也可以使用 SSH。新手优先让 GitHub Desktop 或 GitHub CLI 管理认证，不要把 Token 直接写进网址、脚本和笔记。

凭证不是内容。

永远别提交凭证。

## 八、How：做一次四阶段观察

进入你的练习仓库，先同步并建分支：

```bash
git switch main
git pull
git switch -c docs/understand-sync
```

修改 `学习日志.md` 后，按四个阶段观察。

第一阶段，保存后：

```bash
git status
```

第二阶段，暂存后：

```bash
git add 学习日志.md
git status
git diff --staged
```

第三阶段，提交后：

```bash
git commit -m "docs: 记录本地与远端学习心得"
git status
git log --oneline -3
```

第四阶段，推送后：

```bash
git push -u origin docs/understand-sync
```

去 GitHub 网站切换到该分支，确认提交出现。然后回到终端运行：

```bash
git remote -v
git branch -vv
```

不要只看命令成功。写下每一步变化存在于哪里。

## 九、遇到同步问题时的四问

1. 我当前在哪个本地分支？
2. 这个分支跟踪哪个远端分支？
3. 哪一边拥有另一边没有的提交？
4. 我想获取、整合，还是发送？

问清方向，命令就不难。

把 Push 背成上传、Pull 背成下载，早晚会乱。把本地与远端看作两本需要对账的变化账簿，你就知道每个动作为什么存在。

> 先确认两边的账，再决定往哪边写。
