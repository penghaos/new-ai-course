# Pull Request 是一份变化提案

> 一句话定义：Pull Request 是请求目标分支审查并接纳一组变化的提案，不是一个高级上传按钮。

## 一、都写完了，为什么不能直接合并

你在分支上写完了，测试也过了。为什么还要开 Pull Request，写标题、写说明、等审查？直接把分支合进 `main` 不就完了吗？

一个人练习时，这个问题尤其合理。作者是你，审查者是你，维护者还是你。绕一圈，图什么呢？

我也偷懒过。直接改主线，直接推，快得很。后来某次回头看历史，我知道某个改动是谁做的——当然是我——却不知道当时为什么做、验证过什么、放弃过哪些方案。代码还在，决策丢了。

这时我才明白，PR 保存的不是文件。

是一次接纳变化的理由。

## 二、Commit 回答“改了什么”，PR 回答“为什么值得接纳”

Commit 是变化的历史单位。一个分支里可以有多个提交：增加界面、补测试、修文档。可这些提交为什么属于同一个任务？它们合起来解决了什么问题？风险在哪里？审查者该怎么验证？

这些问题，单个 Commit 不一定能回答。

PR 把一组提交包成一个可讨论的方案：

- 背景是什么；
- 目标是什么；
- 具体改变什么；
- 明确不改变什么；
- 如何验证；
- 有什么剩余风险；
- 谁看过；
- 最终是否接纳。

所以，Commit 是砖。Branch 是施工区。PR 是验收申请。

砖堆好了，不等于房子可以交付。

## 三、Pull Request 这个名字为什么这么别扭

很多中文用户第一次看到“拉取请求”都会困惑：明明是我把代码推上去，为什么叫 Pull？

因为它站在目标仓库维护者的角度说话：请你把我这条分支的变化拉进你的目标分支。

不过，死磕字面意义帮助不大。你真正应该记住的是方向：

- base：接收变化的目标分支；
- compare/head：提供变化的来源分支。

PR 展示的，是来源相对目标新增了什么变化。

方向选反，整份提案就会反。每次创建 PR，先看 base 和 compare。别嫌这一步幼稚。飞机起飞前也会检查方向。

## 四、PR 把私人劳动变成公共判断

你在自己电脑上工作时，很多信息只存在脑子里。你知道为什么这样改，知道哪里没做完，知道哪一处最危险。

一旦提交 PR，这些私人上下文必须被翻译成别人能理解的公共信息。这个翻译过程本身就会暴露问题。

你写“如何验证”时，可能突然发现自己根本没验证。你写“风险”时，可能意识到改动范围超了。你看 Files changed 时，可能发现误提交了 `.env` 或调试文件。

写 PR 不是向别人汇报。

是迫使自己把变化想完整。

## 五、小 PR 为什么比大 PR 更可靠

一个 PR 改 3 个文件，审查者能逐行看。另一个 PR 改 80 个文件，标题叫“重构并增加若干功能”。哪个更容易漏错？

人的注意力是有限的。变化规模越大，理解成本并不是线性增加。因为文件之间还有关系、依赖、顺序和副作用。十个互相关联的变化，不是十份负担，可能是几十种组合。

所以小 PR 的价值不只是“看得快”：

- 目标更单一；
- 验证更明确；
- 反馈更具体；
- 冲突更少；
- 回退更容易；
- 合并更频繁，分支更少偏离主线。

你可能会说，大任务拆不开怎么办？

那通常意味着你还没有找到可独立验证的中间状态。先加基础结构，再迁移一个模块；先在不影响用户的情况下引入新接口，再逐步替换旧实现。拆分本身就是设计能力。

PR 大小，是思考质量的外显。

## 六、Draft PR 是公开的草稿纸

很多人以为 PR 必须等全部完成才开。其实 Draft Pull Request 的价值，恰恰是提前暴露方向。

你做了一个核心骨架，还没写完。若方向可能有争议，早一点开 Draft，让同伴看设计和变化趋势，比三天后完整交付再被推翻便宜得多。

这和写文章一样。标题、提纲、第一节先给编辑看；方向错了，改提纲。全部写完才发现主题错了，谁都痛苦。

Draft 不是“半成品丢给别人”。好的 Draft 要明确：已完成什么、还缺什么、希望别人重点看什么。

提前协作，不等于提前甩锅。

## 七、Review 评论为什么应围绕变化

PR 把讨论绑定在具体差异上。审查者可以对某一行提问、提出建议、批准或请求修改。

好的评论说影响：

```text
这里没有处理空内容。新用户第一次打开时可能看到空白页。
建议增加默认提示，并补一个空数据检查。
```

坏的评论评价人：

```text
你这写得不行。
```

前者让项目变好，后者只让关系变坏。

审查的对象是提议的变化，不是作者的人格。把人和作品分开，是协作能长期进行的前提。

## 八、Merge 只是最终决定，不是质量证明

PR 可以被批准、请求修改、关闭或合并。Merge 表示目标分支接纳了这组变化。

注意，它不表示变化绝对正确。Git 能自动合并，只说明文本历史可以组合；检查全绿，只说明预设规则通过；审查者批准，也可能漏掉问题。

可靠不是一个按钮带来的。

可靠来自多层证据叠加：清楚的问题、合理的改动、小提交、人工审查、自动检查、可回退历史。

GitHub 没有“正确按钮”。

只有“更可靠的流程”。

## 九、How：写一份真正有用的 PR

为你的仓库创建一个 Issue：“在首页增加课程导航”。从最新 `main` 建立分支：

```bash
git switch main
git pull
git switch -c docs/add-course-navigation
```

修改、提交并推送后，创建 PR。使用这个模板：

```markdown
## 背景
新读者打开首页后不知道从哪里开始，解决 #编号。

## 改动
- 新增“学习入口”章节
- 添加各课程链接
- 不修改课程正文

## 验证
- [ ] 在网页中逐一点击链接
- [ ] 手机宽度下检查列表
- [ ] Files changed 中无无关文件

## 风险
文件改名后链接可能失效，后续需要链接检查。

Closes #编号
```

提交前，先自己打开 Files changed，从头到尾读一遍。你会惊讶，作者切换成审查者视角后，能看到多少刚才看不见的东西。

## 十、PR 前的一个判断

别问“我写完了吗？”

问：“我是否提供了足够证据，让别人放心接纳这组变化？”

前者以作者为中心。后者以项目为中心。

> 写完只是劳动结束，合并需要证据开始。
