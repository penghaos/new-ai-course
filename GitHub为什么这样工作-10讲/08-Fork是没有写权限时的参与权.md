# Fork 是没有写权限时的参与权

> 一句话定义：Fork 是你账号下与原仓库保持关联的独立仓库，让你无需原项目写权限也能实验和提议变化。

## 一、开源最反直觉的地方

一个陌生人发现著名项目的文档有错。他没有仓库写权限，也不认识维护者。按传统组织逻辑，他只能发邮件、等授权，或者放弃。

可在 GitHub 上，他可以 Fork 项目，在自己的空间修改，然后向原项目提交 PR。

维护者不必预先信任这个人，也不必先给他写权限。贡献者不必等待授权，就能把想法做成可检查的变化。双方最后在 PR 上讨论是否接纳。

这就是开源协作最精巧的地方：

先允许生产，再决定接纳。

## 二、Star、Fork、Clone 不是三种收藏

新手经常点了 Star，以为项目已经属于自己；或者下载 ZIP，以为可以开始协作。

我们把概念洗干净：

- Star 是收藏和关注信号，不产生副本；
- Fork 在你的 GitHub 账号下创建一个与原项目关联的远端仓库；
- Clone 把某个仓库连同历史复制到本地电脑；
- Download ZIP 只拿到一个时刻的文件，没有 Git 历史和远端关系。

如果你只是以后想找回来，Star。若你想在自己账号下独立实验并可能回馈上游，Fork。若你要在本地工作，Clone。

动作不同，因为意图不同。

先问目的，再点按钮。

## 三、为什么不用一个 Branch 就够了

在同一个团队仓库中，你有写权限，通常可以直接创建功能分支。可开源项目不能给每个路人写权限。那会发生什么，你能想象吧？

Fork 把权限边界移到仓库层。你的 Fork 由你管理，可以自由创建分支、运行实验、打开自己的 Issue。原项目仍由维护者控制。

Branch 是同一仓库内的变化线。Fork 是一个完整的独立仓库，拥有自己的分支、成员、Issue、Actions、标签等，同时与上游保持网络关系。

这不是技术重复。

这是治理边界。

## 四、origin 与 upstream 是两个方向

Fork 后再 Clone，你的本地仓库通常把自己的 Fork 记为 `origin`。为了获取原项目更新，还要增加一个远端，惯例叫 `upstream`：

```bash
git remote add upstream https://github.com/原作者/项目名.git
git remote -v
```

此时：

- 你通常向 `origin` 推送，因为它是你的 Fork；
- 你从 `upstream` 获取更新，因为它是原项目；
- 你向 `upstream` 提 PR，请求接纳变化。

想象一条河：上游产生主项目更新，你的 Fork 是一条支流。你从上游取水，也可以把治理好的变化通过 PR 送回主河道。

方向清楚，命令就清楚。

## 五、开源不等于随便

代码公开，并不意味着你想怎么用就怎么用。License 决定复制、修改、分发和商用的许可边界。CONTRIBUTING 说明项目希望你如何参与。CODE_OF_CONDUCT 说明社区行为预期。

贡献前至少读：

- README：项目解决什么、如何运行；
- CONTRIBUTING：开发与提交规则；
- Issue/PR 模板：需要哪些信息；
- License：法律许可边界；
- Security：安全问题如何私下报告。

这和去别人家做客一样。门开着，不等于你可以重新装修客厅。

开放是一种邀请。

规则是邀请的边界。

## 六、为什么第一次贡献最好从小问题开始

新手常想通过“大改造”证明能力：重写核心模块、换掉全部目录、重做界面。维护者为什么不激动，反而警惕？

因为改动越大，审查成本越高，隐藏假设越多，对项目历史的理解要求越深。你看到的是“更好的方案”，维护者看到的是兼容性、用户迁移、维护负担和未来承诺。

文档错字、失效链接、小型测试、清晰复现，反而是很好的起点。它们让你学习项目流程，也让维护者低成本判断你的沟通和交付质量。

信任不是靠自我介绍获得的。

信任靠一连串小而可靠的交付累积。

## 七、提交 PR 后，工作没有结束

维护者可能要求修改，可能提出你没考虑的边界，也可能因路线不同拒绝。PR 被拒绝，不等于你被拒绝。

好的响应是先理解项目约束，再在同一个分支继续提交并 Push，PR 会自动更新。若意见超出本次范围，可以另开 Issue，而不是无限扩张当前 PR。

别在每次反馈后关闭 PR 重新开一个。那会切断讨论历史。也别把审查意见全部机械照做。若你有证据，礼貌解释；若你不理解，直接问。

协作不是服从。

协作是让理由可见。

## 八、Fork 也有安全边界

公开仓库的 Fork 通常也是公开的，不能把私密改动塞进去。Fork 网络中的提交关系也意味着：删除自己的 Fork，不一定让曾经进入网络的内容彻底不可访问。

从 Fork 创建 PR 时，有时可以允许上游维护者编辑你的分支。这能加速协作，但涉及 Actions 工作流和 Secrets 时要格外谨慎。权限从来不是方便按钮，它代表别人能做什么。

另外，公开项目不等于安全项目。运行陌生代码前，仍应检查安装脚本、依赖、维护活跃度和权限请求。Star 多，只能证明受关注，不能证明没有风险。

人多不等于审计过。

## 九、How：模拟一次开源贡献

先在一个你自己的练习仓库中模拟“上游”，或者选择明确欢迎新手且有贡献指南的公开项目。

标准流程：

```bash
# 先在网页 Fork，再 Clone 自己的 Fork
git clone https://github.com/你的用户名/项目名.git
cd 项目名

# 增加原项目远端
git remote add upstream https://github.com/原作者/项目名.git
git remote -v

# 同步上游主线
git fetch upstream
git switch main
git merge upstream/main
git push origin main

# 创建任务分支
git switch -c docs/fix-one-link
```

只修一个链接或一处明确文档问题。按照项目规则验证，提交并推送：

```bash
git add 具体文件
git commit -m "docs: 修复入门指南链接"
git push -u origin docs/fix-one-link
```

然后从你的 Fork 分支向上游 `main` 创建 PR。标题准确，说明背景、验证和范围。

## 十、Fork 真正改变了什么

它没有取消维护者的决定权，也没有要求贡献者先获得完全信任。

它把“参与生产”和“进入主线”拆开了。

任何人可以先做出一份可检查的提案，维护者再依据证据决定。开放与控制不再只能二选一。

> 不必先获得权力，先做出值得接纳的变化。
