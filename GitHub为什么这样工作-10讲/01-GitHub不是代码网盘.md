# GitHub 不是代码网盘

> 一句话定义：GitHub 是围绕“变化”建立的协作系统，不是存放最终文件的网络硬盘。

## 一、你以为你缺的是一个上传按钮

绝大多数人第一次打开 GitHub，脑子里冒出来的问题都是同一个：

“文件怎么传上去？”

这很正常。我们用惯了网盘。一个文件在电脑里，上传到网上；换一台电脑，再下载回来。问题解决了嘛。

于是你很自然地把 GitHub 也理解成一个网盘。仓库就是文件夹，Commit 就是保存，Push 就是上传，Pull 就是下载。听起来都对。可惜，全错了。

我第一次接触版本控制时也这么想。最让我困惑的是：明明文件已经保存了，为什么还要 add？明明已经 add 了，为什么还要 commit？明明已经 commit 了，为什么网站上还看不见？一个文件而已，搞这么多层，程序员是不是有某种把简单事情复杂化的爱好？

后来我才明白，复杂的从来不是工具。

复杂的是变化。

## 二、文件协作的真正敌人不是丢失，而是混乱

你肯定见过这样的文件：

```text
课程方案.docx
课程方案-修改版.docx
课程方案-最终版.docx
课程方案-最终版2.docx
课程方案-最终版2-领导意见.docx
课程方案-真的最终版.docx
```

笑归笑，我们都干过。

为什么会这样？因为普通文件只能告诉你“现在是什么”，却很难告诉你四件更重要的事：谁改的？改了什么？为什么改？两个人的改动怎么合在一起？

网盘主要解决“放在哪里”。**版本控制解决“怎么变化”**。

这两个问题根本不是一个问题。

一本书的最终稿当然重要。可是当编辑问你：“第二章这个结论为什么删掉？”你若只剩一个最终文件，就只能靠记忆。记忆可靠吗？你连上周三晚饭吃了什么都未必记得，凭什么相信自己能记住半年前的一次改动？

所以，GitHub 的基本单位不是文件。

是变化。

## 三、把变化当成资产，世界就不一样了

假设你写了一篇文章。昨天只有标题，今天补了目录，明天写完第一节。普通文件系统看见的是三个不同时刻的文件。Git 看见的却是一条变化链：

```text
只有标题
  ↓ 提交：补充文章目录
标题 + 目录
  ↓ 提交：完成第一节初稿
标题 + 目录 + 第一节
```

区别在哪里？

普通文件告诉你结果。变化链告诉你过程。

结果能被使用，过程能被理解、审查、组合、撤销、复用。谁更值钱？当然是后者。

工厂里只有成品，没有生产记录，出了问题怎么追查？医院里只有病人当前指标，没有历史检查，医生怎么判断趋势？银行里只有余额，没有流水，你敢把钱放进去吗？

奇怪的是，我们对工厂、医院、银行的记录要求很高，一到自己的工作就只剩“最终版”。

这不是工具问题。

这是你的工作还没有账簿。

Git 就是变化账簿。GitHub 则是把这本账簿搬到网上，再加上任务、讨论、审查、权限和自动检查。说白了，Git 负责记账，GitHub 负责围绕账簿协作。

## 四、Git 和 GitHub 必须分开理解

很多人把 Git 和 GitHub 混成一个词。这样学，后面一定乱。

Git 是安装在电脑上的版本控制系统。没有网络，它照样能记录提交、创建分支、查看历史、合并变化。GitHub 是一家提供在线协作平台的服务。它托管 Git 仓库，又加上 Issue、Pull Request、Review、Actions 等功能。

换句话说：

- Git 处理历史；
- GitHub 处理协作；
- 仓库把两者连接起来。

你可以不用 GitHub 而使用 Git，也可以在浏览器里使用 GitHub 的很多功能而暂时不碰命令行。但只要你开始本地协作，二者就会汇合。

这很难理解吗？

文字处理软件和在线协作文档不是一回事。你可以离线写字，也可以把文档放到网上讨论。Git 与 GitHub 的关系也差不多，只不过它们管理的核心不是一整份文档，而是一组组可追踪的变化。

## 五、Repository 到底是什么

Repository，中文叫仓库。

新手把它理解成“项目文件夹”，这不算错，却远远不够。更有指导意义的定义是：

**仓库是文件、变化历史和协作规则共同构成的项目空间。**

为什么这个定义更有用？因为它会直接改变你的行动。

如果仓库只是文件夹，你会把所有东西一股脑塞进去。如果仓库是项目空间，你就会问：这个文件属于这个项目吗？它应该被追踪吗？别人能理解吗？里面有没有密码和隐私？

如果仓库只是文件夹，你会追求“最新版本”。如果仓库包含历史，你会追求“每次变化都说得清楚”。

如果仓库只是文件夹，你会直接改。若仓库包含协作规则，你会先建任务、开分支、提方案、做检查。

定义决定行动。

## 六、GitHub 为什么适合的不只是代码

你可能会说：“可我不写程序啊。”

没关系。GitHub 最擅长处理纯文本，而文章、课程、提示词、配置、研究笔记，恰好都可以用纯文本表达。**只要一个东西会持续变化、需要多人协作、需要保留历史**，它就可能适合 GitHub。

一本持续修订的书，适合。一个公开课程，适合。一套提示词库，适合。一个团队规范，适合。你甚至可以用它维护简历。

但别走到另一个极端。GitHub 不是所有资料的最佳归宿。大量视频、原始照片、巨型数据集、频繁变动的二进制文件，往往需要对象存储、网盘或专门的数据系统。版本控制有边界。

能用，不等于适合。

## 七、为什么 GitHub 看起来故意多了很多步骤

保存、暂存、提交、推送、PR、合并。步骤确实多。

可每一步都在回答一个不同问题：

- 保存：文件内容写进电脑了吗？
- 暂存：这次准备记录哪些变化？
- 提交：这组变化成为本地历史了吗？
- 推送：别人现在能获得这些提交吗？
- PR：这组变化值得进入目标分支吗？
- 合并：我们正式接纳它了吗？

你看，它们不是同一个动作被拆成六份，而是六个不同决定。

在只有你一个人、文件只改一次的场景里，这些决定显得麻烦。可项目一旦持续半年、参与十个人、每天几十次变化，这些“多余步骤”就变成了秩序。

安全带平时也显得多余。出事时就不多余了。

## 八、How：建立你的第一个变化账簿

现在别急着安装 Git。先用浏览器完成一个最小动作。

1. 登录 GitHub，点击右上角 `+`，选择 **New repository**；
2. 仓库名填写 `my-ai-learning`；
3. 勾选 **Add a README file**；
4. 创建仓库；
5. 打开 `README.md`，点击编辑；
6. 加入一句：`这是我的 GitHub 学习仓库。`；
7. 提交说明不要写 `update`，写：`docs: 说明仓库用途`；
8. 提交后打开历史，看看这个变化如何被记录。

这一步看起来太简单了，是吧？

可你要观察的不是那一句文字，而是“修改前后差异 + 提交说明 + 时间 + 作者”如何一起成为历史。你第一次拥有的不是一个线上文件，而是一笔**可以追溯的变化**。

## 九、你应该带走的新眼镜

以后再打开 GitHub，不要先问：“文件在哪里？”

先问四个问题：

1. 这个项目正在解决什么问题？
2. 最近发生了哪些变化？
3. 这些变化为什么发生？
4. 哪些变化已经被正式接纳？

当你开始用“变化”而不是“文件”观察 GitHub，那些曾经让你头大的 Commit、Branch、PR，就不再是一堆陌生按钮。它们只是管理变化的不同容器。

今天只做一件事：创建仓库，提交一笔说得清楚的变化。

> 别上传最终版。开始记录变化。
