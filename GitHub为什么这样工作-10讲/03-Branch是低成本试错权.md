# Branch 是低成本试错权

> 一句话定义：Branch 是从某个历史节点长出的独立变化线，用来把试验与稳定主线隔开。

## 一、绝大多数人害怕分支，是因为把它想重了

新手看到 Branch，通常会在脑子里想象一件事：把整个项目复制一份。

项目有一万个文件，建一个分支就复制一万个；建十个分支，就复制十万。难怪不敢建。可事实上，Git 分支并不是笨重副本，它本质上只是一个指向某个提交的轻量名字。

说白了，**分支更像书签，不像复印件。**

我第一次听说“一个功能一个分支”时也很抗拒。心想，改两行字还单独建分支？这不是走形式吗？后来我在主分支上改坏过东西，又在一堆未完成修改里紧急修错误，才明白分支省掉的不是磁盘空间。

分支省掉的是恐惧。

## 二、为什么需要一条主线

大多数仓库有一个默认分支，通常叫 `main`。你可以把它理解成项目当前**被正式接纳**的版本。

注意，是“被正式接纳”，不是“永远正确”。主线仍可能有错误，但团队承诺围绕它协作、发布和恢复。

如果所有人都直接改 `main`，会发生什么？甲写到一半，乙推送修复；丙要发布，却发现主线里混着甲没做完的功能。每个人都很忙，项目却无法形成一个可依赖的状态。

餐馆的出餐台上，成品、半成品、实验菜混在一起，服务员敢端哪盘？

主线就是出餐台。分支是后厨工作台。

工作台可以乱，可以试，可以推倒重来。出餐台必须尽量稳定。边界就这么来的。

## 三、分支让“工作”和“接纳”成为两件事

没有分支时，你一动手就影响共同版本。**有分支后，工作可以先发生，接纳可以晚一点决定。**

这叫延迟整合。

你先从 `main` 创建 `feat/search`，开发搜索功能；同伴从同一个 `main` 创建 `fix/login`，修复登录问题。两个人可以并行提交，互不踩脚。修复先完成，就先审查、先合并；搜索功能晚两天也没关系。

```text
main:        A──B────────D
                 \      /
fix/login:        C─────

feat/search:      E──F──G  （仍在继续）
```

分支没有消灭复杂性。它只是把复杂性隔开，让我们在合适的时候处理。

隔离，等待，整合。

## 四、真正宝贵的是可放弃

我们经常只谈分支如何帮助成功，却很少谈它如何允许失败。

你想尝试一个新的目录结构。直接改主线，就会有心理负担：万一不行怎么办？于是你不敢试，或者试了也舍不得扔，因为已经和其他变化搅在一起。

在实验分支里就不同。你可以大胆改。**结果好，提 PR；结果不好，关闭分支**。主线毫发无损。

一个系统若只奖励成功、不允许便宜地失败，人就会减少尝试。创新不是因为大家更勇敢，而是因为失败成本足够低。

Branch 的本质不是分叉。

是**试错权**。

## 五、分支名其实是工作地图

`test2`、`new`、`my-branch-final` 当然能用。但它们几乎不传递信息。

更好的名字会告诉别人变化类型和目的：

```text
feat/add-search
fix/login-timeout
docs/update-install-guide
refactor/split-parser
experiment/new-homepage
```

你打开分支列表，不必逐个询问，就能大致知道项目正在发生什么。分支名把个人工作变成团队可见的地图。

名字不是装饰。

名字是压缩后的上下文。

## 六、为什么要从最新 main 建分支

分支从哪个提交创建，就继承哪个起点。

如果你的本地 `main` 已经两周没同步，而远端主线新增了很多变化，你从旧主线建分支，相当于拿两周前的地图出门。你不是不能到目的地，只是未来合并时更可能遇到冲突和重复工作。

所以每天开始新任务时，常见流程是：

```bash
git switch main
git pull
git switch -c docs/add-reading-list
```

回主线，同步，再开工。

顺序很重要。你若在旧功能分支上直接创建新分支，新分支会把旧任务的提交也带上。后来打开 PR，为什么多出一堆不相干的变化？因为起点错了。

出发前先看地图。很难吗？

## 七、分支不是存档箱

有些仓库一打开，上百个已经合并的分支躺在那里。大家不敢删，仿佛删除分支就会删除成果。

如果变化已经合并到 `main`，对应提交已经进入主线。删除功能分支，只是移除那张临时书签，不会抹掉已经合入的历史。

因此，一个健康的短期功能分支通常经历：创建、工作、推送、PR、合并、删除。

长期不合并的分支会越来越偏离主线，像两座多年不通车的城市。等到终于想合并，冲突、依赖和设计假设全都变了。

分支要短命。

成果要长命。

## 八、分支策略不是越复杂越专业

你可能见过 Git Flow：main、develop、release、hotfix，再配上多种功能分支。复杂项目和特定发布模式可能需要它。

可新手最容易犯的错，是在一个人写笔记的仓库里先设计七层分支制度。工具还没用熟，官僚系统先建起来了。

最小可用规则通常只有三条：

1. `main` 保存被接纳的稳定成果；
2. 每个任务从最新 `main` 创建短期分支；
3. 通过 PR 合并，完成后删除分支。

规则应该解决已经出现的协作问题，而不是表演专业。

够用就好。

## 九、How：做一次可以放心丢掉的实验

在仓库里执行：

```bash
git switch main
git pull
git switch -c experiment/rewrite-title
```

把 README 标题改成一个夸张版本，保存并提交：

```bash
git add README.md
git commit -m "experiment: 尝试新的首页标题"
```

看一下主线与当前分支的差异：

```bash
git diff main...HEAD
```

然后切回主线：

```bash
git switch main
```

你会看到标题恢复原样。实验仍存在于分支，但主线没有变化。

如果你决定不要这个实验，确认没有需要保留的内容后删除：

```bash
git branch -d experiment/rewrite-title
```

若 Git 拒绝删除，说明它检测到未合并提交。不要立刻强制，先确认这些工作是否真的可以丢弃。工具是在保护你。

## 十、以后建分支前只问两件事

第一，这组变化是不是一个独立目的？

第二，如果试验失败，我是否希望能整组放弃？

只要有一个答案是“是”，就建分支。

别把分支当成麻烦。它是在重要项目与不确定尝试之间，替你拉出一张安全网。

> **先隔离变化，才有资格大胆试错**。
