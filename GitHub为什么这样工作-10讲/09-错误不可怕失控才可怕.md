# 错误不可怕，失控才可怕

> 一句话定义：Git 的安全价值不在于让人不犯错，而在于让错误可见、影响有限、恢复有路。

## 一、新手真正害怕的不是 Git，是不可逆

“万一我把代码弄没了怎么办？”

“冲突是不是项目坏了？”

“我刚提交到错误分支，要不要重来？”

这些恐惧都指向同一个东西：你不知道下一步会不会让情况更糟。

我见过最危险的排错方式，也是我自己早年常用的方式：错误一出现，立刻搜索，把前三条命令挨个试。第一条没用，第二条报新错，第三条带着 `--force`，终于“成功”。至于成功覆盖了什么，不知道。

问题不是犯错。

问题是在不知道状态时继续改变状态。

## 二、Git 的第一安全命令不是撤销，是观察

出了意外，先停。别急着 Undo，先搞清变化现在位于哪里。

```bash
git status
git branch --show-current
git log --oneline --decorate -10
git diff
git diff --staged
git remote -v
```

这些命令大多只读取信息。它们回答：当前分支是什么，有哪些未提交变化，暂存区是什么，最近历史如何，连接哪个远端。

医生不会在不知道病人指标时随便下药。财务不会在没对账时直接改余额。你为什么一看到 Git 报错就敢执行破坏性命令？

先观察，后行动。

这是所有排错的母原则。

## 三、冲突不是失败，是工具拒绝替你瞎猜

两个人从同一个起点修改同一区域。甲把标题改成“GitHub 入门”，乙改成“GitHub 深度教程”。Git 能看见两种变化，却不知道项目真正想要哪一个。

于是它停下来，标出冲突：

```text
<<<<<<< HEAD
GitHub 入门
=======
GitHub 深度教程
>>>>>>> other-branch
```

很多人看到尖括号就慌。其实 Git 只是在诚实地说：“文本我找到了，意图请你决定。”

处理冲突不是选择上面或下面这么简单。你可以保留一边，也可以综合成“GitHub 从入门到深入”。关键是最终语义正确，然后删除标记、保存、检查、暂存并继续合并。

冲突需要人，是因为意义属于人。

## 四、如何降低冲突，而不是迷信冲突工具

冲突表面发生在文本，根源常在协作。

两个任务边界重叠，分支长期不合并，大规模格式化混入功能改动，开始工作前没有同步主线，这些都会放大冲突。

降低冲突的办法很朴素：

- 从最新 `main` 建分支；
- 一个 PR 只做一个目的；
- 分支短命，尽早合并；
- 修改公共配置前沟通；
- 不把全局格式化混进功能 PR；
- 用统一自动格式工具减少无意义差异。

最高级的冲突处理，不是在红色标记里手速快。

是让不必要的冲突少发生。

## 五、“撤销”不是一个动作

你说“我要撤销”，至少可能指五件事：

1. 丢掉尚未暂存的文件修改；
2. 把变化移出暂存区但保留文件内容；
3. 修改最近一次尚未共享的提交；
4. 抵消已经推送的某个提交；
5. 重写一段历史。

这些情况影响范围完全不同，当然不能用同一个命令。

最重要的分界线是：历史是否已经共享。

尚未推送的本地历史，你有较大整理自由。已经推送并被他人基于其工作的历史，随意重写会让所有人的账簿对不上。此时通常更安全的方式是 `git revert 提交号`，新增一个反向提交来抵消旧变化。

Revert 承认错误发生过，也清楚记录如何纠正。

历史不是面子。

历史是证据。

## 六、为什么强制命令如此诱人

`reset --hard`、`clean -fd`、`push --force` 都有正当用途。它们的问题不在“邪恶”，而在影响大、保护少。

人在焦虑时最想要一个立刻清净的按钮。工作区乱了，全部清掉；远端拒绝，强推覆盖；历史不好看，直接重写。屏幕终于不报错了，你会误以为问题解决。

可安静不等于安全。

火警器被你拔掉，也不响了。

新手规则很简单：在你能准确说出“它将删除或覆盖哪些对象、是否有恢复路径、是否影响别人”之前，不执行这些命令。

## 七、最严重的错误往往不是代码，是秘密

API Key、Token、数据库密码、SSH 私钥、`.env`，绝不能提交。私有仓库也不行。成员、集成和 Actions 可能读取，账号可能被盗，仓库未来可能公开。

如果秘密已经推送，第一反应常是删除文件再提交。没用。旧内容仍可能存在于历史、Fork、Clone、PR 引用和缓存中。

正确顺序是：

1. 立即撤销或轮换秘密，让旧凭证失效；
2. 评估暴露范围和异常使用；
3. 从当前版本移除并加入 `.gitignore`；
4. 必要时按官方方案协调清理历史；
5. 通知协作者清理旧 Clone，防止再次污染。

GitHub 官方也明确把撤销或轮换秘密放在首位。因为清理历史可能复杂，而让钥匙失效能立刻阻止继续开门。

先换锁，再擦脚印。

## 八、`.gitignore` 不是历史橡皮擦

`.gitignore` 告诉 Git：未来遇到这些尚未被追踪的路径，默认别纳入版本控制。

例如：

```gitignore
.env
.env.*
node_modules/
.DS_Store
*.log
```

可一旦文件已经被提交，后来加入 `.gitignore` 不会让旧历史消失。这就像你告诉摄影师“以后别拍这个人”，之前的照片不会自动蒸发。

预防规则只管理未来。

历史问题要单独处理。

## 九、How：在安全练习仓库制造冲突

只在练习仓库操作。

从同一个最新 `main` 创建两个分支：`experiment/title-a` 与 `experiment/title-b`。分别把 README 第一行改成不同标题，各自提交。

先合并 A 到 `main`。然后切到 B，整合最新主线：

```bash
git switch experiment/title-b
git merge main
```

出现冲突后：

1. 运行 `git status`；
2. 打开冲突文件，读懂两边；
3. 写出一个你真正想要的最终标题；
4. 删除冲突标记；
5. 保存并检查文件；
6. `git add README.md`；
7. 按终端提示完成合并提交；
8. 再次运行 `git status` 和 `git log --oneline --graph`。

你需要的不是“从不见冲突”，而是见到冲突也能保持观察。

## 十、事故发生时的四句口诀

停一下。看状态。分范围。选恢复。

错误并不可怕。没有历史、没有边界、没有检查，才可怕。

> 先保护现场，再决定如何恢复。
