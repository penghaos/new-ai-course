# AI 时代，GitHub 是变化控制系统

> 一句话定义：当 AI 能高速制造变化时，GitHub 用边界、历史、审查和自动化控制变化如何进入真实系统。

## 一、代码变便宜以后，什么变贵了

过去，写一百行代码需要时间。今天，你给 AI 一段要求，它可能几分钟就改完十个文件，再附送测试和文档。

看上去，开发变简单了。

可你有没有想过：当变化的生产速度增加十倍，审查、理解和承担后果的速度也增加十倍了吗？

没有。

代码变便宜，判断变贵。产出变快，责任并没有消失。AI 可以生成一个看似完整的方案，却可能误解目标、扩大范围、引入依赖、泄露数据、写出只覆盖表面场景的测试。

我也有过那种错觉：AI 写完，测试绿了，读起来像那么回事，合并吧。后来发现，最危险的不是明显错误，而是“看起来非常合理”的错误。它让你放弃检查。

AI 不是把 GitHub 变得不重要。

AI 把 GitHub 变得更重要。

## 二、生产变化与接纳变化必须分开

AI 擅长生产候选变化。你描述目标，它创建分支、修改文件、提交、打开 PR。这条生产线会越来越自动。

可候选变化不是被接纳的变化。

Issue 定义任务边界，Branch 隔离工作，Commit 组织变化，PR 提供审查上下文，Review 检查语义，Actions 验证规则，Merge 才表示正式接纳。

你看，前九篇所有概念，在 AI 时代正好组成一条控制链：

```text
目标 → 隔离 → 生产 → 记录 → 提案 → 验证 → 接纳 → 监控与恢复
```

AI 可以参与中间很多环节，但最终系统仍需要明确的责任边界。

速度不是授权。

## 三、Issue 正在从任务单变成代理合同

给人写 Issue，可以依赖共同背景和口头默契。给 AI 写 Issue，模糊处会被它用概率补齐。

“优化一下登录”会发生什么？它可能重构认证、增加依赖、改数据库、重写文案。每一项都能被解释成优化。真正错的也许不是 AI，而是你把愿望写成了任务。

AI 时代的 Issue 更需要：

- 目标状态；
- 允许修改的范围；
- 禁止触碰的边界；
- 完成标准；
- 必须运行的验证；
- 数据与权限限制；
- 失败时如何停止。

这就像一份小型合同。不是为了把一切写死，而是把不可擅自猜测的部分写清。

提示词质量，最终会变成变更质量。

## 四、Diff 是人与 AI 之间最重要的界面

AI 可以写一万个字解释自己做了什么。你最应该看的，仍然是 Diff。

因为语言会概括、遗漏、粉饰，差异直接展示哪些文件增加、删除和修改。AI 说“只调整了错误提示”，Diff 却显示它同时升级了依赖、改了权限配置，你信谁？

当然信变化本身。

审查 AI PR 时先看：

1. 文件范围是否符合授权；
2. 是否修改依赖、权限、网络、数据访问；
3. 是否出现秘密、调试后门或大段生成文件；
4. 测试是否验证真实目标，而非只证明实现自洽；
5. 删除内容是否有意；
6. 复杂度是否超过问题需要。

让 AI 解释 Diff，可以。让解释代替 Diff，不行。

## 五、小任务、小分支、小 PR，在 AI 时代更重要

人写代码慢，大 PR 至少代表付出了很多时间。AI 写代码快，大 PR 可能只代表提示词过宽。

一次改 50 个文件，你很难认真审查；审查不认真，PR 就只剩仪式。于是 AI 的速度把人推向“差不多就合并”，错误也随之批量进入主线。

解决办法不是让人读得更快，而是限制变化批次：

- 一次只解决一个可验证问题；
- 先让 AI 提计划和预计文件范围；
- 核心骨架用 Draft PR 早审；
- 大迁移分阶段，每阶段主线都可用；
- 超出范围的好想法另开 Issue；
- 每次显著修改后重新审查。

流水线速度提高，质检批次就要更小。

这很难理解吗？

## 六、AI Review 不能替代责任人

AI 可以审查 AI 的代码吗？当然可以。它能发现常见错误、可疑模式、缺失测试和一致性问题。让机器先筛掉低级问题，人把时间放在设计和产品影响上，很合理。

可“AI A 写，AI B 审，检查全绿”仍不等于无人负责。两个模型可能共享相同盲区，测试可能围绕错误需求自洽，真正的风险可能位于组织背景、用户承诺或数据治理中。

GitHub 对 Copilot 代理产出的官方指导同样要求彻底审查后再合并；相关保护也把代理 PR 的就绪、批准和合并留给人类流程。

工具可以提供判断材料。

责任不能外包给工具。

## 七、Actions 是自动免疫系统，但免疫系统也会攻击宿主

Actions 可以自动测试、扫描秘密、检查依赖、构建和部署。它像项目的免疫系统，对每次变化执行固定反应。

但工作流本身也是代码，可能拥有 Token、Secrets、写权限和部署能力。来自不可信 Fork 的输入、第三方 Action、日志输出、过大的默认权限，都可能变成供应链风险。

因此自动化要遵循：

- 默认最小权限；
- 第三方 Action 选择可信来源并固定版本；
- 不在日志打印秘密；
- 对外部贡献触发的高权限流程设置人工批准；
- 将生产部署与普通测试分离；
- 定期审查工作流本身。

自动化不是无人管理。

自动化是把管理写成程序。

## 八、GitHub 真正保存的是责任链

一个成熟项目发生事故后，需要回答：

- 哪个 Issue 提出了需求；
- 谁或哪个代理产生变化；
- 哪些 Commit 组成方案；
- PR 里说明了什么；
- 谁审查、谁批准；
- 哪些自动检查通过；
- 哪个版本发布；
- 如何撤销和修复。

这些记录不是为了出事后找替罪羊，而是为了从系统中学习。没有责任链，团队只能靠印象争论；有责任链，才可以改善任务定义、检查规则和权限设计。

审计不是追责文化。

审计是组织记忆。

## 九、How：建立一条 AI 协作工作流

在你的仓库中选择一个小任务，例如“为 README 增加常见问题”。按下面执行：

### 第一步：写 Issue

```markdown
## 目标
新手能在首页找到三个常见问题的答案。

## 允许范围
只修改 README.md。

## 禁止范围
不修改课程正文，不新增依赖，不移动文件。

## 完成标准
- [ ] 包含账号、Push、PR 三个问题
- [ ] 每个答案不超过 120 字
- [ ] 所有已有链接仍可用
```

### 第二步：让 AI 先给计划

要求它列出预计修改文件、具体段落、验证方法和风险。计划超出范围，先纠正，不要让它边做边扩张。

### 第三步：在独立分支工作

```bash
git switch main
git pull
git switch -c docs/add-faq
```

让 AI 只修改授权文件。提交应小而清楚。

### 第四步：打开 Draft PR

在说明中附上 Issue、变更摘要、人工验证和 AI 参与范围。先看文件列表，再逐行看 Diff。

### 第五步：双层审查

先运行自动检查或 AI Review，再由你判断目标、边界、准确性和读者体验。修订后重新检查显著变化。

### 第六步：合并与回顾

满足标准后合并。关闭 Issue。然后写一句复盘：这次哪个约束最有用，哪个检查缺失，下次如何改进。

这才叫使用 AI 工作。

不是把键盘交出去。

## 十、十篇文章最终只讲了一件事

GitHub 不是代码网盘。Commit 不是保存。Branch 不是副本。Push 不是合并。PR 不是手续。Issue 不是抱怨单。Review 不是挑刺。Actions 不是万能绿灯。Fork 不是收藏。Git 也不是一串神秘命令。

它们共同解决同一个问题：

**我们如何让变化被看见、被解释、被隔离、被验证、被接纳，并在出错时能够恢复。**

以前，变化主要由人缓慢制造。现在，AI 可以高速制造变化。生产能力越强，控制系统越重要。

你真正要学会的，不是按按钮。

是管理变化。

今天开始，用 Issue 定义一个小问题，用分支隔离它，用 Commit 记录它，用 PR 证明它值得被接纳。

> AI 负责加速变化，你负责决定什么进入世界。
