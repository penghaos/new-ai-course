# 第 5 课：冲突、安全、Actions 与进阶路线

## 5.1 冲突不是 Git 坏了

当两条分支修改同一文件的同一区域，Git 能看见两种结果，却不知道人真正想保留哪个，于是暂停并请人决策。

冲突标记通常像这样：

```text
<<<<<<< HEAD
来自你当前分支的内容
=======
来自要合并分支的内容
>>>>>>> other-branch
```

处理步骤：

1. 先读两边内容，不急着删除；
2. 决定保留 A、保留 B，或融合成第三种正确结果；
3. 删除全部冲突标记；
4. 保存并实际检查最终文件；
5. 暂存并提交冲突解决结果。

命令行中常见流程：

```bash
git status
# 手工编辑冲突文件
git add 冲突文件
git commit
```

不同合并情境可能提示继续执行特定命令，以终端提示和 `git status` 为准。

## 5.2 降低冲突的办法

- 开始任务前同步最新 `main`；
- 一个 PR 围绕一个目的，尽快合并；
- 大文件或公共配置修改前先沟通；
- 不做与任务无关的全局格式化；
- 团队约定统一格式，并交给自动工具处理；
- Issue 中标记负责人，避免重复开发。

冲突不是只能靠工具解决的问题，很多冲突其实源自任务边界和沟通不清。

## 5.3 撤销的安全梯度

Git 的撤销命令很多，因为“撤销”可能指不同状态：

1. 只想丢掉尚未提交的文件修改；
2. 想把文件移出暂存区，但保留修改；
3. 想修改最近一次本地提交；
4. 想撤销已经共享到远端的提交；
5. 想重写一段历史。

新手原则：**先确认状态，再选择撤销方法。已经共享的历史优先新增一个反向提交，不轻易改写。**

先收集信息：

```bash
git status
git log --oneline --decorate -10
git diff
git diff --staged
```

对于已经推送并被别人使用的提交，通常使用 `git revert 提交号` 创建一个明确的“撤销提交”，比强制推送安全。

不要在不理解后果时复制执行 `reset --hard`、`clean -fd` 或 `push --force`。它们可能让未保存工作难以恢复。

## 5.4 秘密泄露：删除文件还不够

以下内容永远不应提交：

- API Key、个人访问令牌、数据库密码；
- SSH 私钥、证书私钥；
- `.env`；
- 客户数据、身份证件、私人聊天记录；
- 带真实凭证的配置样例。

正确方式：提交 `.env.example`，只保留变量名和假值：

```dotenv
OPENAI_API_KEY=请在本地填写
DATABASE_URL=请在本地填写
```

如果秘密已经提交或推送：

1. **立即在服务提供方撤销或轮换秘密**；
2. 评估谁可能访问、是否已被自动抓取；
3. 从当前文件移除并加入 `.gitignore`；
4. 必要时按 GitHub 官方指导清理历史；
5. 通知受影响的维护者并记录事件。

第一步永远是让旧秘密失效。仅删除 GitHub 页面上的文件，历史里可能仍然存在。

## 5.5 下载和运行陌生项目的安全边界

公开仓库不代表安全。运行前：

- 看维护活跃度、发布记录和 Issue；
- 阅读安装脚本，不盲目复制带管理员权限的命令；
- 检查依赖、License 和安全策略；
- 在隔离环境中测试；
- 不给不必要的文件、账号和网络权限；
- 不把自己的真实密钥直接交给陌生代码。

Star 数量是流行度信号，不是安全审计结论。

## 5.6 GitHub Actions：让规则自动执行

Actions 的基本模型：

```text
事件 Event → 工作流 Workflow → 作业 Job → 步骤 Step → 结果
```

例如：每次提交 PR 时，自动检查 Markdown 是否存在坏链接。

工作流文件通常位于：

```text
.github/workflows/某个名称.yml
```

一个只用于理解结构的示例：

```yaml
name: hello-actions

on:
  workflow_dispatch:

jobs:
  say-hello:
    runs-on: ubuntu-latest
    steps:
      - name: 输出问候
        run: echo "GitHub Actions 正在运行"
```

`workflow_dispatch` 表示允许手动触发。提交后，在 Actions 页面选择工作流并运行，观察日志。

### Actions 的价值

- 把“每次都应该检查”变成自动执行；
- 给每个 PR 一致反馈；
- 合并后自动构建或部署；
- 留下机器执行的记录。

### Actions 的风险

- 第三方 Action 本质上是在运行代码；
- 工作流可能接触仓库 Token 或 Secrets；
- 权限过大会放大供应链攻击；
- 来自 Fork 的不可信输入需要格外小心。

只使用可信来源，固定版本，授予最小权限，不在日志中打印秘密。新手先会读结果，再逐步编写复杂工作流。

## 5.7 Release、Tag 与版本

- **Tag**：给某个提交贴一个稳定标签，如 `v1.0.0`；
- **Release**：围绕某个 Tag 发布说明和可下载产物；
- **Commit**：日常变化单元，不等同于正式版本。

项目达到一个可供他人使用的稳定节点时再发布 Release。发布说明应告诉使用者：新增、修复、重大变化、升级方法和已知问题。

## 5.8 AI 编程时代，为什么更要学 GitHub

AI 可以快速生成大量变化，但不能替你承担最终责任。GitHub 提供的是控制 AI 产出的结构：

1. Issue 定义目标和边界；
2. 分支隔离 AI 的尝试；
3. Diff 让你只看变化；
4. 小提交让错误容易定位和回退；
5. PR 让人和机器共同审查；
6. Actions 反复验证规则；
7. 历史记录说明每次决定如何形成。

面对 AI 生成的 PR，不要只问“代码能不能跑”，还要问：

- 它是否只改了授权范围内的内容？
- 是否偷偷扩大依赖、权限或数据访问？
- 测试是否真的覆盖核心风险？
- 是否引入看似方便但无法维护的复杂度？
- 我是否能解释并负责合并后的结果？

## 5.9 进阶学习路线

### 第一阶段：熟练日常流

反复完成：`status → diff → add → commit → pull → push → PR`。目标是看到状态就知道下一步，而不是背命令。

### 第二阶段：读懂历史与差异

学习 `git log`、指定提交的 diff、文件历史、blame 的合理用途。重点是调查“某个决定何时、为何发生”，不是追责个人。

### 第三阶段：安全撤销与整合

学习 revert、restore、merge、rebase 的差异。先在练习仓库制造场景，绝不拿重要项目当实验场。

### 第四阶段：治理与自动化

学习分支保护、CODEOWNERS、Issue/PR 模板、Actions、Release、Secrets 和依赖安全。

### 第五阶段：维护开源项目

学习版本策略、贡献者管理、安全披露、License、路线图和社区沟通。此时 GitHub 已从工具变成治理基础设施。

## 5.10 专家真正关心的问题

- 历史是否可理解，而不只是存在？
- 主线是否随时可发布或可恢复？
- 权限是否符合最小权限原则？
- 自动检查覆盖的是真风险，还是只有表面绿灯？
- 依赖和工作流的供应链是否可信？
- 一个关键维护者离开后，项目是否还能运转？
- 发生事故时，能否快速回答“哪个变化、何时、为何、由谁批准”？

这些问题决定 GitHub 使用水平的上限。

## 本课验收

- [ ] 能解释冲突为何需要人做语义判断；
- [ ] 遇到意外会先运行只读检查，而不是连续试命令；
- [ ] 知道共享历史优先用 revert，不随意强制推送；
- [ ] 知道秘密泄露后第一步是撤销或轮换；
- [ ] 能解释 Actions 的事件、工作流、作业和步骤；
- [ ] 能说明 AI 生成代码为什么仍需分支、Diff、PR 和检查。
