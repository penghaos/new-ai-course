# 第 4 课：团队协作与开源贡献

## 4.1 协作的核心不是“都会 Git”

真正高效的团队会把四件事说清楚：

1. **做什么**：Issue 与完成标准；
2. **谁在做**：负责人、分支和进度；
3. **改了什么**：Commit 与差异；
4. **是否接纳**：PR、Review、检查与合并决定。

GitHub 把这些记录放在一起，让协作不依赖“谁记得微信群里说过什么”。

## 4.2 写一个可执行的 Issue

差的 Issue：

```text
首页不好用，改一下。
```

好的 Issue：

```markdown
## 问题
新读者打开首页后，不知道课程从哪里开始。

## 期望结果
README 首屏出现清楚的“从这里开始”入口。

## 完成标准
- [ ] 链接到第 0 课
- [ ] 说明课程对象和完成时间
- [ ] 手机页面无需横向滚动

## 不包含
本任务不重写全部课程内容。
```

关键不在篇幅，而在减少不同人对“做完”的不同理解。

## 4.3 写一个容易审查的 PR

PR 说明建议包含：

```markdown
## 背景
它解决什么问题？关联哪个 Issue？

## 改动
- 改了什么
- 明确没改什么

## 验证
审查者如何复现或检查？

## 风险
最可能出错的地方是什么？如何回退？

Closes #编号
```

PR 越大，审查者越容易疲劳和漏错。一个 PR 尽量围绕一个目的；大需求拆成可以独立验证的小步。

## 4.4 Code Review 不是挑刺

审查的共同目标是让项目更可靠，同时让知识在团队中流动。

审查顺序：

1. 先看 PR 背景和 Issue，确认问题值得解决；
2. 看文件列表和总体变化，判断范围是否异常；
3. 逐文件看差异；
4. 按作者提供的方法验证；
5. 区分“必须修改”“建议修改”“个人偏好”；
6. 给出明确结论：批准、评论或请求修改。

有帮助的评论：

```text
这里没有处理空内容。用户第一次打开时可能看到空白页。
建议增加默认提示，并补一个空内容场景的检查。
```

不太有帮助的评论：

```text
不行，重写。
```

评论针对变化和影响，不针对人的能力。提问常比武断命令更有效：“这里选择这种方式，是为了兼容什么情况？”

## 4.5 三种常见合并方式

| 方式 | 结果 | 适合 |
|---|---|---|
| Merge commit | 保留分支所有提交并增加一次合并提交 | 希望完整保留分支结构 |
| Squash and merge | 把 PR 压成一个提交进入主线 | 小型功能、想让主线整洁 |
| Rebase and merge | 把提交线性地接到主线 | 提交本身已整理得很清楚 |

新手不必争论“唯一正确方式”。先遵守项目约定。个人练习可优先 Squash，让主线每个提交对应一个完整 PR。

## 4.6 Star、Watch、Fork、Clone 的区别

| 动作 | 作用 | 是否产生你的副本 |
|---|---|---|
| Star | 收藏、表达关注 | 否 |
| Watch | 订阅项目通知 | 否 |
| Fork | 在自己的 GitHub 账号下创建关联副本 | 是，远端副本 |
| Clone | 把仓库复制到本地电脑并保留历史 | 是，本地副本 |

Fork 常用于你没有原仓库写权限时：在自己的 Fork 中建分支、修改和推送，再向原仓库发 PR。

## 4.7 第一次开源贡献流程

### 第一步：先读规则

在目标仓库寻找：

- `README.md`
- `CONTRIBUTING.md`
- `CODE_OF_CONDUCT.md`
- Issue / PR 模板
- License

项目公开可见不等于你可以随意复制、再发布或商用；许可由 License 决定。

### 第二步：选合适任务

新手可以关注 `good first issue`、`documentation`、`help wanted` 标签。先确认 Issue 未被认领，必要时礼貌留言：

```text
你好，我想尝试处理这个问题。我准备先补充复现步骤和文档示例，预计两天内提交 PR。这个方向合适吗？
```

不要同时占用多个任务，也不要在未理解需求时提交大规模重写。

### 第三步：Fork 与 Clone

在页面点击 **Fork**，创建到自己账号。然后克隆自己的 Fork：

```bash
git clone https://github.com/你的用户名/项目名.git
cd 项目名
git remote add upstream https://github.com/原作者/项目名.git
git remote -v
```

通常：

- `origin` 指向你的 Fork，你可以推送；
- `upstream` 指向原项目，用于同步。

### 第四步：同步主线并建分支

```bash
git fetch upstream
git switch main
git merge upstream/main
git push origin main
git switch -c docs/fix-install-guide
```

### 第五步：小改动、小提交、充分验证

只修改 Issue 范围内的内容。提交前查看 `git diff`，执行项目要求的测试或检查，并记录验证方法。

### 第六步：推送并向原项目发 PR

```bash
git push -u origin docs/fix-install-guide
```

创建 PR 时确认目标是“原作者仓库的 main”，来源是“你的 Fork 中的分支”。在说明中关联 Issue，诚实写明验证范围。

### 第七步：响应反馈

维护者要求修改时，在同一个分支继续提交并推送，PR 会自动更新。不要因为有意见就关闭 PR 重新开一个，也不要把讨论当作对个人的否定。

## 4.8 权限与保护

小团队至少应考虑：

- 不让所有人默认拥有管理权限；
- 保护 `main`，要求通过 PR 合并；
- 对关键项目要求至少一位审查者；
- 要求自动检查通过；
- 限制强制推送和直接删除主分支；
- 离职或合作结束后及时撤销权限。

规则不是不信任人，而是减少人在忙碌、误解或疲惫时造成不可逆损失。

## 4.9 团队模拟练习

即使只有你一个人，也可以扮演三个角色：

1. 产品角色：创建 Issue，写清完成标准；
2. 贡献者角色：建分支、修改、提交、开 PR；
3. 审查者角色：隔十分钟再看差异，留下至少一条具体审查意见，修订后再合并。

任务建议：为 `my-ai-learning` 添加 `CONTRIBUTING.md`，说明如何贡献一条学习资源。

## 本课验收

- [ ] 会写包含背景、改动、验证和风险的 PR；
- [ ] 能区分 Star、Watch、Fork、Clone；
- [ ] 能解释 `origin` 和 `upstream`；
- [ ] 知道如何给出具体、尊重且可行动的审查意见；
- [ ] 参与开源前会先读贡献指南和 License。
