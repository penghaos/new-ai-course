# 练习参考答案

答案用于核对思路，不要求逐字一致。先自己回答，再来看。

## 第 0 课

### 1. 私有仓库能不能提交 API Key？

不能。私有仓库的成员、集成和自动化仍可能读取，账号可能被盗，仓库未来也可能改成公开。凭证应放在本地环境变量或 GitHub Secrets 等专用秘密系统中。

### 2. Desktop 和网站是不是两套历史？

不是。它们是同一 Git 仓库工作流的不同入口。Desktop 操作本地仓库，推送后与 GitHub 远端同步；网站展示远端历史和协作信息。

### 3. 为什么账号密码不能进行 Git 认证？

GitHub 已移除 Git 操作的密码认证。HTTPS 应使用浏览器授权、凭证管理器或个人访问令牌，也可使用 SSH。

## 第 1 课

### 1. Git 和 GitHub 的区别

Git 是可离线工作的版本控制系统，负责记录、比较和组合变化；GitHub 托管 Git 仓库，并增加账号、权限、Issue、PR、Review、Actions 和开源社区。

### 2. 为什么 push 不等于 merge？

Push 只是把本地提交发送到对应远端分支；Merge 是把一条分支的变化组合进另一条分支。把功能分支推到 GitHub，不会自动改变 `main`。

### 3. 为什么不直接修改 main？

独立分支可以隔离未完成变化，让人和机器在进入稳定主线前检查，也支持多人并行和安全放弃实验。

### 4. Issue、Commit、PR 如何连接？

Issue 定义要解决的问题；一个或多个 Commit 记录解决过程中的变化；PR 把这些提交作为一个方案提交审查，并在合并后关闭 Issue。

### 5. 为什么不同文件通常能自动合并？

Git 能计算两条分支相对共同起点的差异。若变化位于不重叠区域，它可以同时应用；只有语义或文本位置无法自动判断时才需要人处理。

## 第 2 课关键问题

### PR 为什么不等于提交？

提交是 Git 历史中的变化节点；PR 是 GitHub 上围绕一组提交进行讨论、检查和决定的协作对象。

### PR 为什么不等于合并？

PR 是提案。它可以被讨论、修改、关闭或拒绝；只有执行 Merge 后，变化才进入目标分支。

### 删除已合并分支会不会删除成果？

不会。成果对应的提交已经进入 `main`。删除的是完成任务后不再需要的分支引用。

## 第 3 课

### Save、Add、Commit、Push 的区别

- Save：编辑器把内容写进工作区文件；
- Add：选择某些变化进入暂存区；
- Commit：把暂存内容记录为本地历史节点；
- Push：把本地提交发送到远端。

### 为什么有时网站看不到刚提交的内容？

Commit 默认只发生在本地，尚未 Push；或已经推到了功能分支，但网站当前查看的是 `main`。

### Fetch 和 Pull 的区别

Fetch 获取远端状态和提交信息，但不自动整合到当前分支；Pull 通常等于 Fetch 后再进行整合，因此改变当前本地分支的可能性更大。

### `.gitignore` 为什么不能抹掉已经提交的秘密？

它只告诉 Git 以后忽略匹配且未被追踪的路径，不会重写已有历史。泄露凭证必须先撤销或轮换。

## 第 4 课

### Star、Watch、Fork、Clone

- Star：收藏；
- Watch：订阅通知；
- Fork：在自己 GitHub 账号下创建关联远端副本；
- Clone：在本地创建带 Git 历史的副本。

### origin 和 upstream 是什么？

它们是远端地址的惯用昵称。在 Fork 工作流中，`origin` 通常指自己的 Fork，`upstream` 通常指原项目；名称可以改变，真正含义应通过 `git remote -v` 查看。

### 为什么 Review 不只是找错误？

Review 还用于确认需求、传播背景、改善可维护性、记录权衡并形成共同所有权。好的意见具体说明影响和可行行动。

## 第 5 课

### 为什么冲突不能总自动解决？

Git 能比较文本，但不知道业务意图。如果两种变化都合理或需要第三种组合，人必须决定最终语义。

### 为什么共享提交优先 revert？

Revert 新增一个反向提交，不改变别人已经获得的历史；重写并强推共享历史会让他人的分支与远端不一致。

### 秘密泄露后第一步是什么？

立即撤销或轮换，让旧凭证失效。清理文件和历史是后续控制传播与降低风险的步骤。

### Actions 绿灯为什么不等于正确？

自动检查只验证被编写进去的规则和场景。规则可能不完整、配置可能错误，也无法代替对需求、安全、体验和长期维护的人工判断。

## 结业口试

1. **保存后网站没变化**：只改了本地工作区。
2. **Commit 后同伴看不到**：提交还在本地，尚未 Push。
3. **Push 后 main 没变化**：提交在功能分支，尚未经 PR Merge。
4. **绿灯仍需审查**：自动测试覆盖有限，人要判断目标、边界、风险和可维护性。
5. **冲突需人判断**：工具不一定知道两种文本背后的正确业务意图。
6. **Token 删除文件不够**：历史和缓存可能保留；先撤销或轮换才能停止继续使用。
7. **AI 改 40 个文件如何控风险**：暂停合并，按目标拆分，检查文件范围和权限变化，要求小提交与验证，删除无关改动，再用 PR 和自动检查逐步接纳。

## 最后提醒

遇到与答案不同的情况时，先问自己四个问题：

1. 我当前在哪个仓库和分支？
2. 变化现在位于工作区、暂存区、本地历史还是远端？
3. 我想保留什么，想改变什么？
4. 下一步是否会影响已经与别人共享的历史？

能稳定回答这四个问题，你就很少需要靠运气操作 Git。
