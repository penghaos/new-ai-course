# 第 2 课：只用网页完成第一次协作

这一课不安装任何工具。你将在浏览器里完整走一遍 GitHub Flow：仓库 → 分支 → 提交 → Pull Request → 审查 → 合并。

## 2.1 创建第一个仓库

登录 GitHub，点击右上角 `+`，选择 **New repository**。

按下面填写：

- Repository name：`my-ai-learning`
- Description：`我的 AI 学习知识库，也是我的 GitHub 练习场`
- Visibility：初学阶段可选 Private；想作为公开作品集可选 Public
- 勾选 **Add a README file**
- 暂不添加 `.gitignore` 和 License

点击 **Create repository**。

### 你刚刚做了什么

GitHub 创建了一个远端仓库、默认分支 `main`、一个 `README.md` 文件，以及包含该文件的首次提交。

仓库网址一般是：

```text
https://github.com/你的用户名/my-ai-learning
```

## 2.2 看懂仓库首页

- **Code**：文件和目录；
- **Issues**：问题、需求和任务；
- **Pull requests**：待讨论和待合并的变化；
- **Actions**：自动检查和工作流；
- **Insights**：活动、贡献、流量等；
- **Settings**：权限、规则和仓库设置。

文件列表上方通常能看到当前分支 `main`、提交数量和最近一次提交。

## 2.3 先创建一个 Issue

打开 **Issues** → **New issue**，填写：

```markdown
标题：建立学习日志

## 背景
我需要记录每次学习 GitHub 的过程。

## 完成标准
- [ ] 新增 `学习日志.md`
- [ ] 写明日期和本课收获
- [ ] 在 README 中加入学习日志链接
```

创建后记住 Issue 编号，例如 `#1`。

### 为什么不直接改文件

Issue 把“为什么做”和“做完是什么样”写在修改之前。个人项目也值得这样做，因为未来的你同样会忘记当初的意图。

## 2.4 创建分支

回到 **Code**。点击当前分支名称 `main`，在输入框写：

```text
docs/add-learning-log
```

选择 **Create branch: docs/add-learning-log from main**。

分支名建议使用小写英文和短横线：

- `docs/...`：文档；
- `feat/...`：新功能；
- `fix/...`：修复；
- `chore/...`：整理或维护。

### 检查点

页面左上当前分支应为 `docs/add-learning-log`。**动手前永远先看自己在哪个分支。**

## 2.5 新建文件并提交

在该分支选择 **Add file** → **Create new file**，文件名输入：

```text
学习日志.md
```

内容可写：

```markdown
# 我的学习日志

## 第一次练习

- 日期：填写今天日期
- 我完成了：创建仓库、Issue 和分支
- 我理解了：分支是安全的独立变化线
- 我还困惑：Pull Request 为什么不是直接合并
```

选择提交时，确认提交到当前分支，而不是 `main`。提交说明写：

```text
docs: 新增 GitHub 学习日志
```

点击 **Commit changes**。

### 好提交的三个标准

1. 只做一件可说明的事；
2. 提交后项目处于合理状态；
3. 说明让别人不用看细节就知道变化目的。

“update”“改一下”“最终版”都太含糊。

## 2.6 再修改 README

仍在 `docs/add-learning-log` 分支，打开 `README.md`，点击编辑按钮，在末尾加入：

```markdown
## 学习入口

- [查看我的学习日志](./学习日志.md)
```

提交说明：

```text
docs: 在首页添加学习日志入口
```

现在分支里有两个提交。它们分别表达“创建内容”和“连接入口”，比一个模糊的大提交更容易审查。

## 2.7 创建第一个 Pull Request

进入 **Pull requests** → **New pull request**，确认：

- base：`main`，要接收变化的目标分支；
- compare：`docs/add-learning-log`，提出变化的来源分支。

先看 **Files changed**。绿色通常表示新增，红色表示删除。PR 标题填写：

```text
docs: 建立学习日志
```

描述填写：

```markdown
## 做了什么
- 新增学习日志
- 在 README 添加入口

## 为什么
用于记录本课程每次练习，解决 #1。

## 如何检查
- 打开 README，点击“查看我的学习日志”
- 确认链接能正常进入文件

Closes #1
```

`Closes #1` 会在 PR 合并后自动关闭对应 Issue。这把“问题”和“解决方案”连在了一起。

点击 **Create pull request**。

## 2.8 像审查者一样检查自己

即使只有一个人，也先做自审：

1. PR 标题能否概括变化？
2. `Files changed` 里有没有意外文件？
3. Markdown 链接能否点击？
4. PR 是否满足 Issue 的三个完成标准？
5. 有没有隐私、密钥或不该公开的材料？

在 PR 下留一句评论：

```text
已自查：链接可用，文件内容正确，没有额外改动。
```

这不是形式主义，而是在练习把“我觉得没问题”变成“我检查了哪些东西”。

## 2.9 合并并清理分支

点击 **Merge pull request** → 确认合并。随后点击 **Delete branch** 删除已完成的功能分支。

删除分支不会删除已经合入 `main` 的内容；它只是清理已经完成任务的临时变化线。

回到 **Code**，切到 `main`，检查：

- `学习日志.md` 已存在；
- README 链接可点击；
- Issue #1 已关闭；
- Pull Request 显示 Merged。

## 2.10 故意做一次可控实验

新建分支 `experiment/change-title`，把 README 标题改掉并提交。然后打开 PR，但**不要合并**。观察 base、compare、Commits 和 Files changed，最后关闭 PR 并删除分支。

你会发现：提出变化不等于接纳变化；关闭 PR 也不会伤害 `main`。这就是安全实验的价值。

## 本课验收

- [ ] 有一个 `my-ai-learning` 仓库；
- [ ] Issue #1 记录了任务和完成标准；
- [ ] 两次小提交位于功能分支；
- [ ] PR 描述包含“做了什么、为什么、怎么检查”；
- [ ] PR 合并后 Issue 自动关闭；
- [ ] 已删除完成任务的分支；
- [ ] 能解释为什么 PR 不等于提交，也不等于合并。

如果全部完成，你已经掌握 GitHub 最核心的协作闭环。
